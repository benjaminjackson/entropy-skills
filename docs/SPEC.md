# Spec

This file is the source of truth. The skill, hook, and README are implementations of it and can be regenerated from it. When they disagree with this file, this file wins. When a decision changes, change it here first.

## Intent

A language model cannot act randomly. Asked for something unique, it predicts the most likely "unique" and lands on the same result every run. Real variety has to come from outside the model. This plugin pulls a random string from the shell and makes the model derive every creative decision from that string, so each run starts from a different place. The technique is String Seed of Thought (Sakana AI).

The plugin must work for any task where variety beats the default: visual design, prose, naming, code architecture. It must not be tied to one domain.

## What must be true

1. `/entropy:inject` gets its seed from `openssl rand -base64 48`. The model never invents, edits, or shortens it.
2. The model reads the task, infers the domain, and picks the three to six decisions that most shape the result in that domain. For each one it writes a menu of 8 to 12 options that span the whole space, including the default and its opposite. The seed is hashed into numbers and each number, modulo the menu size, picks one option. The arithmetic is shown. Every decision traces back to the string through a pick the model could not steer.
3. The model commits to where the seed points. Judgment makes the direction good. Judgment never steers it back toward the default.
4. The seed and the derived direction are both shown in chat. The seed string never appears in the deliverable.
5. Every inject appends one JSON line to `.entropy/seeds.jsonl` (timestamp, seed, task, scope, direction) and overwrites `.entropy/current.json` with the same object.
6. With a task in the arguments, the skill does the task after showing the direction, then reads the result back against each axis and rewrites if it drifted from a pick. With no task, it stops and waits.
7. `--seed <string>` replays a seed. When the seed is in the log, the recorded menus are reused and the picks reproduce exactly; when it is not, menus are written fresh. The seed is hashed again either way; the logged direction is a record, not an input. `--current` re-states the direction in `current.json` without generating. `--headless` suppresses every question for the rest of the session.
8. A direction ends with a scope line: the deliverable named in the task. Work inside that deliverable inherits the direction. Work outside it does not, unless the user says so. No task means the scope is everything.
9. The user's standing rules win over the seed. Before the direction is written down, each axis is checked against CLAUDE.md, active skills, and the task's own constraints. Conflicting axes are dropped and named.
10. When the model delegates work inside the scope, it pastes the seed and direction into the subagent's prompt.
11. A hook prints a one-line reminder on every prompt while `current.json` exists, so the direction survives compaction. The reminder tells the model to read the file. Nothing from the file is echoed, because the file may come from a cloned repository and its text is not trusted.
12. When it is unclear whether new work is inside the scope, the model asks. Under `--headless` it applies the direction and says so.
13. In a git repository where `.entropy/` is not ignored, the skill asks whether to add it to `.gitignore`. Under `--headless` it does not ask and does not touch the file.
14. The direction is never quietly softened later in the conversation. If the user asks for a change, the change is applied and the rest of the direction is kept.

## Decisions and why

**One seed at a time. A new inject replaces the old direction.** The simplest thing first. The log keeps history, and branching is done by copying a seed from the log into a fresh conversation with `--seed`. Forking the conversation itself does the same job, so a pipeline of branches inside the plugin is not a requirement.

**Deferred, and wanted later.** These came up in the interview and are planned, not rejected: layering a new seed on top of the current direction, selected by an argument, with replace as the default; rerolling one axis while keeping the rest; an outcome note on a log entry (kept, rejected, branched from), set by a separate skill. Each is an addition on top of the current shape, not a change to it.

**Scope is the deliverable the task names, not a leaky-or-scoped switch.** The first draft applied a direction to "later work of the same kind." That was wrong: a README and a commit message are the same kind, but the README is not part of that commit message. Mood and voice feel like they should leak because they belong to a whole, and the whole was what the task named. Sentence structure for one commit message should not leak because that message was the whole. Same rule, different noun. A user who wants a project-wide mood names the project in the task.

**The user's rules win.** The seed varies taste inside the box the user set. It never overrides house style, accessibility, correctness, or explicit constraints. This was violated once in practice: a "leave out motivation" axis pushed the why out of a commit body that the user's commit skill required. The check in item 9 exists because of that.

**Subagents get the direction pasted in.** They cannot see the conversation. Without this, delegated pieces silently revert to the default.

**The reminder hook is one line and telegraph-terse.** It runs on every prompt, so it must cost almost nothing when active and print nothing when not. It does not repeat the scope. Echoing file text into every prompt was flagged twice as a prompt injection path, so the model reads the file for the scope instead.

**`--headless` sticks for the session.** It exists for scripts. Passing it on every call is the failure mode it prevents.

**`.entropy/` is the user's call.** The log could be committed to share seeds with collaborators, or ignored as scratch. The skill asks once rather than deciding.

**Replay reuses the logged menus.** The first shape re-derived everything from the string and accepted that a replay might not match. That held while the options were fixed lists in the skill. With model-written options, the menus are the part that changes between runs, so hashing the same seed against fresh menus gives different picks and a seed alone reproduces nothing. Now `--seed` looks the seed up in `.entropy/seeds.jsonl`; if found, the recorded menus are read back verbatim and only the hash and picks are redone, so the direction reproduces and the arithmetic is still shown. A seed not in the log gets fresh menus and a warning. The log stays a plain record: the direction is never copied, and the new line carries a `from` field naming the line it replayed.

**Enumerate, then select. Never read the string for inspiration.** The first version asked the model to read the string for patterns and derive a direction from what it saw. The first eval showed that fails: five seeds gave five near-identical directions (hard consonant names, ledger metaphors, deadpan tone, bone paper with one red accent), because every base64 string looks the same to a model and its reading of it is not random. Scores were 4 versus 2 for design and 2 versus 2 for prose and naming. The fix follows Sakana's actual procedure: list the candidates first, then use the string as a number to choose among them. Randomness reaches the decision as selection, not interpretation. The menu is now the only place the model's taste can narrow the result, so the skill requires menus that include the default, its opposite, and options the model would not choose on its own.

**Wide menus, never bad ones.** The second eval showed picks were random but menus were narrow in one place: register. Every result was quiet and contemplative, and every prose piece a domestic vignette, because the model never listed anything else. The first proposed fix was to force registers like brash or cheesy onto the menu. Rejected: the user does not want bad work, only different good work. The rule instead is that every axis's options must each be doable well, and two axes are mandatory on every task: register, with a named set of ten respectable voices, and frame, the scene or reference tradition the piece is built on. Variety comes from the width of good traditions, not from lowering the floor.

**Check execution against the pick.** The third eval showed the dice choosing warm, austere, conversational, and wry across runs while the judge read every piece as the same lyrical voice. Selection was random; execution drifted back. So after doing the task, the model reads the result against each axis and rewrites where it drifted. A required axis for the concrete scenario a prose piece opens on was proposed and rejected: the plugin is not aimed at creative writing, and randomizing content rather than form does not serve the user. Prose is in scope when asked for, but its subject is the user's, not the seed's.

**Roll the accessories, not only the skeleton.** With layout, frame, palette, and type rolled, every design still came out wearing the same micro-type: an uppercase letter-spaced eyebrow on all 20 pages, a hairline rule under the headline, a tiny mono meta bar, a stat strip on about 12 of 20, one phrase flipped to warm orange, and copy that refuses gamification. These are the widely recognized tells of model-made pages, and they live in decisions the seed left unrolled. So five more axes are mandatory for visual work: micro-type ornament, headline treatment, section rhythm, copy stance, and motion. Each menu includes the model's own habit as one option and "none" as another. The hash now yields twenty numbers instead of twelve so every axis gets its own. The eval for this change ran with twenty runs per arm, because the ten-run design evals swung between 5.7 and 8.0 on dice alone.

## What the eval must show

The claim is: outputs vary more with the skill than without. The eval runs the same open creative prompt several times in each of two arms, one with the plugin and one without, and a judge scores the set for distinctness of color, structure, voice, or whichever axes fit the prompt. The plugin arm must score higher. A regenerated skill that fails this is wrong, however faithful its wording.

The eval runs on Opus by default, never Fable. A model argument accepts `opus`, `sonnet`, or `haiku` so the same suite can check whether the skill holds up on smaller models.

The eval is a plain script, `evals/run.sh`, that loops `claude -p` for each arm, scores each arm's set of outputs three times with the responses shuffled, and puts the two sets head to head, blind and in random order, on two judge models. The ship gate: on every prompt, the plugin's mean beats the baseline by at least 2 points, and the plugin set wins every head-to-head on both judges. Ten runs per arm. Five runs was too few: two runs rolled the same frame by chance and moved a score by three points. Two reasons. First, `claude plugin eval` is early access at the time of writing and is absent from the public docs, so a regenerated plugin cannot depend on it. Second, its graders score one run at a time, and variety is a property of the set. The script runs both arms with `--setting-sources ""` so the user's hooks and other plugins do not shape either arm. `--bare` would also drop CLAUDE.md, but it requires an API key in the environment, which not every user has. Prompts live in `evals/prompts/`, one file each, covering design, prose, naming, and code so the any-domain claim is tested. Prompts do not name the product: a name like Tally pulled every design toward tally marks and ledgers in both arms.

Result at version 0.1.0, Opus generating, ten runs, three passes:

| prompt | with plugin | without | head-to-head wins, Opus judge | head-to-head wins, Sonnet judge |
|---|---|---|---|---|
| code | 6.0 | 2.0 | 3 of 3 | 3 of 3 |
| design | 8.0 | 2.0 | 3 of 3 | 3 of 3 |
| naming | 7.7 | 2.0 | 3 of 3 | 3 of 3 |
| prose | 5.7 | 2.0 | 3 of 3 | 3 of 3 |

Every head-to-head was won at the maximum margin. Design scored 4.3 before its own round of fixes: the frame picks differed, but six or seven of ten hero sections collapsed into one specimen-sheet layout on bone paper, because frame changes the costume and not the body, and because a model reading its own CSS confirms anything. Three changes took it to 8.0 with zero spread across passes: a mandatory layout-skeleton axis with named shapes, a read-back that renders the page with headless Chrome or Playwright and states ground color, skeleton, and type from the screenshot, and an eval judge that sees screenshots instead of CSS. A second run of the same design eval scored 5.7 (5 to 6), so between-run noise on design is about two points and the honest claim is 5.7 to 8.0. Both runs still passed the gate. The shared pattern that survives every seed: an editorial poster with a giant flush-left headline, one phrase flipped to a warm accent color, uppercase micro-labels, and copy that refuses gamification. With the five accessory axes added, a twenty-run design eval scored 8.0 with zero spread, fidelity 95% (151 of 159 picks honored). The tell is weaker, not dead: only 3 of 20 pages rolled the uppercase eyebrow, yet 16 of 20 still carry uppercase letter-spaced micro-type, because stamps, running heads, folios, and callout labels all get set the same way, and the judge still names a "letterspaced uppercase masthead line" as the shared pattern. The refusal copy also leaks into subheads and footers on pages whose copy stance rolled something else. So two rules were added: the ornament pick governs the treatment of all small type, and uppercase tracked small type is allowed only under the eyebrow pick; the copy stance pick governs every line on the page, and the read-back names the stance of each line. Twenty more runs: still 8.0 with zero spread, fidelity 89% (140 of 158), uppercase small type on 4 of 20 pages, exactly the 4 that rolled the eyebrow, refusal copy on 2 of 20. The eyebrow tell is gone. What the judges name now is a warm paper ground with one saturated accent on about half the set, which comes from the model writing warm-paper options into several palette slots, and the product being named Ledger or Verso in several runs, since the product name is not rolled. Two more rules followed: one slot per habit on any menu, and a name-shape axis when the task supplies no name. Twenty runs: 8.0 with zero spread, fidelity 94%, uppercase small type 3 of 20, refusal copy 1 of 20, every product name different. Judges now name the hero grammar itself as shared (small wordmark, one oversized headline, a short lede, one solid rectangular button, a three-across fact strip) and a quiet literary copy voice. Those are the next layer.

**Menus are written by procedure, not from habit.** The dice are fair; the menu is where taste hides, and every shared pattern the evals found was a menu written from habit: ten quiet voices, three cream slots, no eyebrow slot at all. So run-time menus follow two steps: name the habit first and give it one slot; read the menu back and check every pair of options apart before hashing. The menus are recorded in `current.json` so the eval can grade them, since a checklist the model finds tedious gets skipped. Twenty runs under the procedure: still 8.0 with zero spread, fidelity 87%, uppercase small type 4 of 20, refusal copy 0 of 20, and generation time doubled from six minutes to twelve. Menus passed the four checks 81 of 225 times. Most failures were the grader reading the skill's own fixed lists: register options are mood words with no concrete behavior, sidebar-and-canvas is a species of asymmetric split, "all one color and one weight" names a property rather than a move. That is a fair audit of the fixed lists, not of the run-time menus, so the lists were rewritten as concrete moves: each register states what its sentences do, each layout is a shape a reader could tell apart from across the room, and each headline treatment is one move rather than a property. The four-step procedure was cut to the two steps that had matched failures seen in an eval: name the habit and give it one slot, and check every pair of options apart before hashing. The other two, naming the goal of the axis and walking traditions, either duplicated the pair check or targeted text the skill controls. Twenty runs on that: 7.7 (7 to 8), fidelity 92%, menus passing 101 of 207, generation nine minutes. The grader still called the run-time register menus adjectives, because the model copies the names from the fixed list into its menu and leaves the behaviors behind, and it found the same pairs alike in motion and name shape that it had found before, since those lists had not been rewritten.

**Fixed axes, model-written options.** What the fixed lists bought was never the ten register names or the eleven layout shapes. It was forcing the model to treat register, layout, eyebrow, headline, copy stance, and name as decisions at all; a model writes menus only for the decisions it knows it is making, and the eyebrow was on 20 of 20 pages because it was never seen as a choice. The options are a different matter: the hand-written lists broke the menu rules in their own way, and the model-written ones in theirs. So each mandatory axis now carries the name of the decision, one sentence on what a reader should be able to tell from the result, the line naming the model's habit as one slot, and three examples that show how far apart options sit and are marked as not the menu. The options are written fresh each run under the two rules. The habit line stays because it is step one of the procedure in a single sentence and has done the most work of anything in the lists. Twenty runs on that: 8.0 with zero spread, menus passing 136 of 219, the best yet, uppercase small type 2 of 20, refusal copy 0 of 20, fidelity 81%, the lowest yet, generation twelve minutes. The three shapes side by side: four-step procedure with the old lists, 8.0 variety, 87% fidelity, 36% menus; two steps with lists rewritten as moves, 7.7, 92%, 49%; two steps with axes only, 8.0, 81%, 62%. Variety is pinned at 8 whatever the menus look like, so the menu work shows up only in the menu grade and in what the judges name as shared. The fidelity dip is one run and unexplained; the likely cause is that fresh menus hold options the model finds harder to execute than its own list did. Tuning stops here. What the judges name as shared now is the brief itself: a flat typographic poster with one headline and one button and no photograph, which is what a hero section in one HTML file with inline CSS and no images can be. What judges name as shared now is the hero grammar (oversized headline, short lede, one solid rectangular button, no photograph ever) and a one-word literary product name with dry understatement.

**A thing on most pages is a missing axis, not a bad menu.** The eyebrow was on 20 of 20 pages, the stat strip on most, refusal copy on most, and cream ground sat under several palette names. No menu rule would have removed any of them, because a model writes menus only for the decisions it knows it is making, and none of those had been named as one. The menu grader audits the options the model wrote; only a person looking at a contact sheet of twenty results finds the decision that was never on a menu. So the maintenance rule: after each eval, look at the contact sheet, and anything shared by most pages that the brief did not require becomes a new mandatory axis with its habit line, not a rule in the treatment text. The design arm has had this look several times. The prose arm has not, and carries only the two axes every domain gets; its own tells, an opening question, "not X but Y", the rule of three, are the next candidates once someone reads twenty prose results side by side.

Variety says the outputs differ; it does not say each output is what its seed asked for. `evals/fidelity.sh <results-dir>` checks that: for each plugin run it hands the judge the screenshot and the direction and asks, axis by axis, whether the page honors the pick. Measured over the three saved design runs: 90% before the layout axis and render read-back, 96% after, 94% on the rerun. Roughly three misses in seventy either way, so the render read-back did not measurably raise fidelity; the layout axis did the work on variety, and the render step stays because it is what lets the read-back catch a wrong ground or skeleton when one happens, and because the judge needs the screenshot anyway.

Rendering depends on the machine. A Mac with Chrome renders through headless Chrome. The cloud container has Playwright with Chromium preinstalled and ImageMagick 6, so it renders through Playwright, which needs the page as a `file://` URL. Confirmed in the container: the screenshot is written and the model can open it. The session's browser tools (the built-in Claude Browser, Claude in Chrome) run on the user's machine and cannot open a file that lives only in the container. Where nothing renders, the read-back falls back to the code and says so.

The contact-sheet look that finds missing axes has been done on the design arm only. Prose, naming, and code have not had it, so their 20-of-20 tells are unknown.

A second check: every direction line in a run's output shows the menu index and the arithmetic that chose it. A direction without the arithmetic is the model choosing for itself.

## Files

- `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`: manifests.
- `skills/inject/SKILL.md`: the procedure, implementing items 1 through 13.
- `evals/fidelity.sh`: per-run check that a rendered design honors its picks and that its menus pass the four checks; reads a saved results directory.
- `hooks/hooks.json`, `hooks/remind.sh`: the reminder, item 11.
- `README.md`: install and usage.
